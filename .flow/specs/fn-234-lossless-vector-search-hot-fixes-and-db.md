## Goal & Context
<!-- scope: business -->
<!-- Source: 35% user / 25% [paraphrase] / 40% [inferred] -->

Production vector retrieval on large GNO indexes (1.34M stored vectors in a ~31 GB SQLite database) takes 10.4–11.2 s per query on both scoped (`--collection`) and unscoped cold CLI invocations, making semantic and hybrid search unusable at scale even when a clean `vec0` mirror exists. Independent profiling and code inspection show that four concrete, strictly lossless issues account for a major share of avoidable latency and database bloat before any `vec0` layout migration or approximate indexing is introduced:

1. **Cold-process and post-write `vec0` regression (`hasNullCosineVariant` defect):** Before taking the clean-mirror `vec0` fast path, `hasNullCosineVariant` executes `SELECT 1 FROM vector_variants WHERE partition_id = ? AND vec_distance_cosine(embedding, embedding) IS NULL LIMIT 1`. On any healthy partition (zero all-zero vectors), `LIMIT 1` never triggers early exit, so the guard scans every stored vector BLOB in the partition and computes `vec_distance_cosine` on every row (~1.9 µs/vec warm, ~8–9 s cold/overflow at 1.34M vectors). Because the result is cached only in process memory and keyed on `vector_variant_epoch.epoch`, every cold CLI search and every document/chunk write forces a full `vector_variants` scan before `vec0` runs, completely masking the v2.16.0 `vec0` fast path (`10.4–11.2 s` unscoped vs `10.4–11.0 s` scoped).
2. **Pre-ranking work on the fallback and batched exact SQL paths:** `searchVectorVariantsFromVariants` and `searchVectorVariantsBatch` unconditionally join `content_chunks` for every eligible row (even when no chunk-language filter is active) and run `GROUP BY o.variant_id, o.mirror_hash, o.seq` with `json_group_array(o.document_id)` across the entire eligible domain before computing top-`k` distances. At 500k–1.34M vectors this creates millions of B-tree probes and a huge temp sort/aggregation before selecting top-20 results.
3. **SQLite I/O thrashing and 4 KB overflow pages:** GNO hardcodes `PRAGMA mmap_size = 268435456` (256 MB) and `PRAGMA cache_size = -64000` (64 MB primary / 32 MB secondary) and never sets `PRAGMA page_size` (defaulting to 4,096 bytes). Every 1024-dim float32 vector BLOB (4,096 B plus row overhead) spills onto an overflow page, turning 1.34M vectors into ~6 GB of scattered page reads per search against a 256 MB mmap window and also pressuring the `0.3–0.4 s` fusion/hydration stage.
4. **Leftover legacy vector tables and `similar` hydration regressions:** After v1 variant partitions activate, legacy `vec_<hash>` tables (such as an observed ~5 GB `vec_53f6e8f9` table on a 31 GB index) and superseded `content_vectors` rows are never pruned, and `createVectorIndexPort` eagerly creates `vec_<hash>` on writable opens even when v1 is already active. Separately, scoped `listDocumentsForSimilarity` combines `collection = ?` with `(id IN (...) OR mirror_hash IN (...))`, causing SQLite to scan the entire collection via `idx_documents_collection` + Bloom filters instead of `MULTI-INDEX OR`, while CLI `gno similar` still loads the entire collection or database via `listDocuments()` to hydrate at most 200 hits.

This spec ships first as a strictly lossless foundation (100% exact ranking, zero `vec0` layout migration, zero re-embedding) so cold CLI and resident retrieval immediately recover the `vec0` fast path, fallback SQL scans drop avoidable pre-ranking work, database bloat can be reclaimed safely, and sibling specs for partitioned `vec0` and quantized rescoring build on clean SQLite I/O and durable mirror metadata. **What this spec changes by itself (plan review and benchmark spike, 2026-11-23).** Deployments that always search with `--collection` stay on the exact SQL path, so R1 does not shorten their vector stage. R2's `content_chunks` skip is the scoped gain: the spike measured 13 to 25% off the exact scan at every selectivity from 0.1% to 90% (450k-vector partition, 1024 dimensions, warm). R3's `mmap_size` tops out at 2,147,418,112 bytes on the bundled SQLite; one cold run at 1.34M vectors took the float32 `vec0` scan from 3.9 s to 2.1 s, with at least 10% run-to-run noise in the same series. R4 returns disk space only after an explicit vacuum. The order-of-magnitude win for large scopes arrives with Spec 2's `bit` coarse mirror. This spec makes the exact paths that Spec 2 falls back to cheaper and makes the clean-mirror fast path reachable from a cold process.

## Architecture & Data Models
<!-- scope: technical -->

### 1. Durable per-partition null-cosine tracking (eliminating `hasNullCosineVariant` scans)
- **Storage:** add a nullable `null_cosine INTEGER` column (`0 | 1`, `NULL` = unknown) to the existing `vector_mirror_state` row. `hasNullCosineVariant` is read only after `isMirrorClean` passes (`variant-search.ts`, fast-path guard), so the flag is needed only while the clean row exists. Migration 036's delete-only triggers already remove that row on every raw `vector_variants` change, which invalidates the flag with it. No new table and no new triggers.
- **Downgrade behaviour:** an older binary restores the row with `INSERT OR REPLACE INTO vector_mirror_state (partition_id, dirty)`, which resets `null_cosine` to `NULL`. Unknown is the safe state: the reader falls back to the probe.
- **Exact predicate on write:** `VectorVariantStore.writeRows` evaluates `vec_distance_cosine(?1, ?1) IS NULL` in SQL for each written or updated embedding. A JS `sumSq === 0` check is wrong: sqlite-vec accumulates in float32, so `vec_distance_cosine(v, v)` is `NULL` for a vector with components of `1e-30` (squares underflow) and for one with components of `1e30` (squares overflow), while a double `sumSq` is non-zero and finite for both. Verified on `sqlite-vec 0.1.9`.
- **Maintenance inside `keepingMirrorMark`:** the store reads `(dirty, null_cosine)` before the write and restores both after it.
  - Prior `0` and no written embedding is null-cosine: restore `0`.
  - Any written embedding is null-cosine: restore `1`, whatever the prior value.
  - Prior `NULL`: stays `NULL` unless a written embedding is null-cosine.
  - `removeUnowned()` on a prior `1`: restore `NULL`, so the next maintenance pass recomputes.
- **Authoritative computation:** `syncPartitionIndex`, `rebuildPartitionIndex`, `syncIndex()` and `activate()` run the existing `LIMIT 1` probe once inside their write transaction and persist the result with the clean mark.
- **Backfill for existing databases:** migration v38 only adds the column. sqlite-vec is not loaded during migrations, and the probe is a multi-second scan on large indexes. The flag is filled by the next `gno vec sync`, `gno vec rebuild`, activation, or the guarded persist below.
- **Guarded persist after a read:** a search runs inside a deferred read transaction, often on a query-only connection, so it never writes inside its snapshot. When the search had to run the probe, it records the `vector_variant_epoch` it saw. After the snapshot ends it runs, on the writer connection, `UPDATE vector_mirror_state SET null_cosine = ? WHERE partition_id = ? AND dirty = 0 AND null_cosine IS NULL AND (SELECT epoch FROM vector_variant_epoch WHERE id = 1) = ?`. The write is best-effort: a busy or locked writer, a query-only process without a writer, or a changed epoch skips it. The in-memory per-connection cache stays as the fallback.
- **Read path:** `hasNullCosineVariant` reads `null_cosine` with the clean mark (one primary-key lookup). A non-`NULL` value answers without touching `vector_variants`.

### 2. Drop the unconditional `content_chunks` join on exact scans
- In `searchVectorVariantsFromVariants` and the filtered/dirty batched scanner (`searchVectorVariantsBatchInSnapshot`), join `content_chunks` inside the candidate subquery only when `options.eligibility?.language` is set. `proveUnknownOwners` already joins `content_chunks` for the surviving candidates and marks an owner whose chunk row is missing as unproven.
- Owners without a chunk row now enter ranking and are dropped after proof. Parity then rests on the existing expansion: `limit *= 4` in the single-query path, and the single-query fallback when a batched heap underfills (`results.length < k && totalEligibleRows > cap`). Parity tests must include an index where chunk rows are missing for bound owners.
- **Measured:** 13 to 25% faster than the v2.16.0 scan at every selectivity. The resulting scan costs about 1.9 µs per eligible vector warm, against 1.5 µs for a float32 `vec0` scan, so little is left for a deeper restructure to recover.
- **Deferred (see Boundaries):** ranking distinct `variant_id`s before grouping owners. Review found two hazards that the first draft did not specify. A top-L cut by `(distance, variant_id)` can drop a variant tied at the boundary distance whose `mirror_hash` sorts earlier, which breaks the `(distance, mirrorHash, seq, variantId)` order. Owner hydration for the winning variants must also re-apply the full eligibility filter, or owners from other collections leak into `documentIds`. Spec 2 keeps this scan as the route for every filtered search and for every scope under its exact-cost budget, so its output contract must not move.

### 3. SQLite `mmap_size` and `cache_size` tuning
- **`mmap_size`:** the bundled SQLite (3.53.2 under Bun 1.4.2 on Linux) is compiled with `MAX_MMAP_SIZE=0x7fff0000`. `PRAGMA mmap_size = 8589934592` reads back as `2147418112`. SQLite maps a prefix of the file, so on a database larger than the cap the pages past it still use ordinary reads. Request `min(cap, floor(totalmem * 0.5))` on 64-bit platforms, keep 256 MB on 32-bit, read the effective value back with `PRAGMA mmap_size`, and expose it in `gno doctor`. Keep the try/catch so clamping or an unsupported filesystem never fails open. macOS and custom SQLite builds may report a different cap, so the code trusts the read-back value.
- **One helper for three sites:** `open()`, `openReadOnly()` and `openReadDb()` in `src/store/sqlite/adapter.ts` each set these PRAGMAs today. Move them into one function.
- **`cache_size`:** raise the primary cache to `-131072` (128 MiB) and the read connections to `-65536` (64 MiB).
- **Soak thresholds:** file-backed mmap pages count toward RSS. Run `bun run soak --tier smoke` before and after. A bounded-growth finding is a finding against this change, and no threshold in `scripts/soak/config.ts` is loosened.
- **`page_size` stays at 4096 (rejected by the spike).** At 100k vectors and 1024 dimensions, 16 KB pages made `vector_variants` 18.6% larger (439.6 MB to 521.4 MB) and the exact scan 16% slower (154.3 ms to 179.4 ms). Only the float32 `vec0` scan improved (137.3 ms to 95.9 ms), and Spec 2 does not route large scopes there.
- **Measure the live-file cost before designing around it.** The spike's freshly built files show about 1.9 µs per vector on the exact scan. A long-lived ~31 GB index showed about 8 µs. Fragmentation and cold cache are the suspected causes and neither is measured. R6 records the exact scan on a copy of a large real index before and after `VACUUM INTO`.

### 4. Legacy vector table hygiene and safe reclamation
- **Stop eager legacy `vec_<hash>` creation when v1 is active:** in `createVectorIndexPort`, skip `CREATE VIRTUAL TABLE IF NOT EXISTS vec_<hash>` when the model has an activated partition in `vector_partitions`. Today `searchNearest` and `searchNearestBatch` return `VEC_SEARCH_UNAVAILABLE` unless the legacy statement exists or the connection is query-only (`!(searchStmt || noVectorsYet)`). Add a third state, "no legacy table, partition active", that runs `searchVectorVariants` and leaves the legacy statements null. `rebuildVecIndex` and `syncVecIndex` must not recreate the table in that state.
- **Older binaries:** a pre-v38 binary recreates an empty `vec_<hash>` on a writable open. That is harmless and small. The next prune removes it.
- **Explicit reclamation (`gno vec prune`, surface settled against `spec/cli.md`):** one `BEGIN IMMEDIATE` transaction that drops legacy `vec_<hash>` tables and deletes legacy `content_vectors` rows for models with an activated partition, and drops `vec_v1_<partition>` tables that have no `vector_partitions` row. Search authority already ignores `content_vectors` for a model once any of its partitions has activated, so the condition matches what retrieval reads.
- **sqlite-vec is required:** `DROP TABLE` on a `vec0` table fails with `no such module: vec0` on a connection that has not loaded the extension. Prune fails closed with a clear error when sqlite-vec is unavailable, as `dropVectorPartition` already does.
- **Readers of `content_vectors` (verified after review):** `src/store/vector/freshness.ts`, `src/store/vector/status.ts` and `src/cli/commands/doctor.ts` already read the activated partition first. `src/store/vector/stats.ts` (`countVectors`, `countBacklog`, `getBacklog`) and `inferDimensions` in `src/cli/commands/vec.ts` read `content_vectors` directly. Each of their callers must be shown to run only before activation, or be switched to the active partition, before prune deletes rows.
- **Disk space:** prune reports reclaimed rows and tables and states that the file shrinks only after a vacuum. The documented path for large indexes is `VACUUM INTO` a new file, which leaves the original as the rollback copy and also defragments the vector rows. The spike confirmed `VACUUM INTO` runs from a WAL database. An in-place `--vacuum` flag stays explicit. Neither runs on a normal command.

### 5. `similar` hydration parity and query-plan fix
- **Scoped `listDocumentsForSimilarity`:** drive the query from the id and hash lists. `json_each(?) j CROSS JOIN documents d` on the primary key for the `id` leg, and `json_each(?) j CROSS JOIN documents d INDEXED BY idx_documents_mirror_hash` for the `mirror_hash` leg, with `d.collection = ?`, `d.active = 1` and `d.mirror_hash IS NOT NULL` applied after the seek. Verified: a plain `UNION` of the two `IN` forms still scanned `idx_documents_collection` with a Bloom filter on the `mirror_hash` leg, and the `json_each`-driven form gave primary-key and `idx_documents_mirror_hash` seeks only.
- **CLI `gno similar`:** Use `store.listDocumentsForSimilarity(...)` with the hit `documentIds` and legacy `mirrorHashes` instead of `store.listDocuments(doc.collection)` / `store.listDocuments()`, achieving parity with REST and MCP hydration.

## API Contracts
<!-- scope: technical -->

- **No breaking changes** to `StorePort`, `VectorIndexPort`, CLI JSON/Markdown outputs, MCP tools, REST routes, or SDK return shapes.
- All search ranking scores, `minScore` thresholds, `NULL` cosine distance handling, and tie-break ordering `(distance, mirrorHash, seq, variantId)` remain **bit-for-bit identical** to v2.16.0.
- `gno vec prune` (or `gno vec sync --prune-legacy` — exact CLI surface settled during implementation against `spec/cli.md`) returns structured JSON + human-readable counts of dropped legacy tables and deleted legacy `content_vectors` rows, and refuses to drop legacy vectors for any model lacking an activated v1 partition.
- Forward SQLite migration (v38) is strictly additive and idempotent on existing v37 databases; older databases without the v38 table/column gracefully fall back to the existing probe.

## Edge Cases & Constraints
<!-- scope: technical -->

- **Rollback safety and raw SQL mutations:** the flag lives on the `vector_mirror_state` row, so migration 036's existing delete-only triggers remove it on every raw `vector_variants` change. Uncommitted outer transactions must not poison connection-level caches, and the guarded persist never runs inside a search snapshot.
- **Read-only connections (`PRAGMA query_only = 1`):** A read-only connection that encounters an unpopulated null-cosine mark must not attempt a write; it falls back cleanly to a connection-local probe without failing the query.
- **Owners without chunk rows:** dropping the `content_chunks` join lets an owner whose chunk row is missing reach ranking. Proof rejects it and the existing expansion refills the result, so output stays identical to v2.16.0.
- **Shared-host / low-RAM safety:** `PRAGMA mmap_size` and `cache_size` must remain safe on low-memory containers/CI and 32-bit platforms, never failing open when the OS clamps `mmap_size`.
- **No automatic `VACUUM`:** no open, migration or query path vacuums. `page_size` stays at its current default in this spec.
- **No legacy data loss:** Legacy pruning must never delete `content_vectors` or `vec_<hash>` for a model whose v1 partition is still `shadow` or absent, and must never delete active `vec_v1_<partition>` mirrors.
- **Zero other-product references:** No external product names in code, specs, commits, docs, or site copy.

## Decision Context
<!-- scope: both -->

Part of a two-spec vector scaling series designed from live production profiling on a ~39k-document / 1.48M-chunk / 1.34M-vector / ~31 GB database, two synthetic benchmarks (50k and 200k vectors), and a benchmark spike at 46.8k real vectors and 100k, 500k and 1.34M synthetic vectors:

- **Spec 1 (this spec):** Strictly lossless hot fixes and DB hygiene. It removes the cold-CLI double scan (`hasNullCosineVariant`), drops the unconditional `content_chunks` join on exact SQL paths, raises `mmap_size` to the build cap and `cache_size`, enables safe reclamation of leftover legacy `vec_<hash>` tables, and fixes `similar` hydration.
- **Spec 2 (depends on Spec 1):** a `bit` coarse `vec0` mirror partitioned by collection, with exact float32 rescore and a cost-based router. It merges the former Spec 2 (collection-partitioned float32 mirror) and Spec 3 (quantized two-stage search). The spike showed the float32 partitioned mirror is within about 25% of the exact scan, so it was dropped.

Shipping Spec 1 independently delivers immediate cold-CLI and DB-hygiene wins with zero `vec0` mirror rebuild and zero recall risk, while fixing the `hasNullCosineVariant` defect that would otherwise negate Spec 2's `vec0` fast path on every cold CLI call. We explicitly rejected keeping `hasNullCosineVariant` as an in-memory-only cache (cold CLI always pays the full scan) and rejected triggering automatic `VACUUM` on migration (unsafe/slow on 30+ GB files).
